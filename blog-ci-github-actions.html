📌 为什么手动 publish-blog 已经很顺,还要做 CI?

在上一篇 Happy + Claude Code：7×24 在线 里，我们已经有了 publish-blog 脚本 — 一行命令就能把 HTML 推到 nginx。看起来已经够轻了。 但用了几天后发现三个新需求:

  1. 多设备时,"哪台机器是真相"开始模糊。手机上 Happy 改一段，笔记本又改一段，最后到底谁对？
  2. 万一服务器挂了,博客就没了。webroot 里的 HTML 没有别的副本。
  3. 想把发布过程暴露在 git history 里 — 每篇文章对应一个 commit，回滚改动是 git revert 一行。

解法是让 git 仓库成为唯一真相，CI 负责把仓库内容同步到 webroot。 这样:

  • 多设备协作: 谁先 push 谁赢，冲突走 git rebase
  • 天然备份: GitHub 是天然异地副本
  • 历史可回滚: git revert + push，CI 自动把旧版重新部署
  • 本地写作不用 ssh: git push 就完事

🛠 实现拆解

1. 专用 deploy key (ed25519)

关键决策: 不要复用个人 SSH key。给这个仓库单独生成一对，写明用途，方便以后撤销。 

# 服务器上生成,不带密码 (CI 没法输入密码)
ssh-keygen -t ed25519 -N "" \
  -f ~/.ssh/blog_deploy_ed25519 \
  -C "blog-shiyao-pro-deploy@github-actions"

# 公钥追加到 authorized_keys
cat ~/.ssh/blog_deploy_ed25519.pub >> ~/.ssh/authorized_keys

公钥末尾的注释字段 blog-shiyao-pro-deploy@github-actions 是关键 — 哪天想撤销，一行 sed 就行:

sed -i '/blog-shiyao-pro-deploy/d' ~/.ssh/authorized_keys

2. 把 secrets 喂给 GitHub

用 gh CLI 一句话搞定，不用进 web UI:

# 私钥从文件读,不会回显到日志
gh secret set DEPLOY_SSH_KEY < ~/.ssh/blog_deploy_ed25519
gh secret set DEPLOY_HOST --body "47.x.x.x"
gh secret set DEPLOY_USER --body "shiyao"

gh secret list   # 验证

3. workflow 全文

这是真正在跑的 .github/workflows/deploy.yml:

name: Deploy to blog.shiyao.pro

on:
  push:
    branches: [main]
    paths:
      - '**.html'
      - '.github/workflows/deploy.yml'
  workflow_dispatch:

concurrency:
  group: deploy-blog
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          port: 22
          command_timeout: 3m
          script_stop: true
          script: |
            set -euo pipefail
            REPO=~/projects/blog-shiyao-pro
            WEBROOT=/var/www/blog.shiyao.pro

            cd "$REPO"
            git fetch --quiet origin main
            git reset --hard origin/main

            sudo rsync -av --delete --prune-empty-dirs \
              --exclude='.*' \
              --exclude='*.bak' --exclude='*.bak.*' \
              --exclude='nginx/' --exclude='scripts/' \
              --include='*.html' \
              --include='*/' \
              --exclude='*' \
              --no-perms --no-owner --no-group \
              "$REPO/" "$WEBROOT/"

            sudo chown -R nginx:nginx "$WEBROOT"
            sudo find "$WEBROOT" -type f -exec chmod 644 {} \;
            sudo find "$WEBROOT" -type d -exec chmod 755 {} \;

            # smoke test
            curl -fsS -o /dev/null -w "Home: %{http_code}\n" https://blog.shiyao.pro/
            curl -fsS -o /dev/null -w "Post: %{http_code}\n" https://blog.shiyao.pro/happy-claude-247

几个关键设计:

  • concurrency.group — 同时只能一个部署在跑，避免新旧 push 互相打架
  • git reset --hard origin/main — 比 git pull 干净，能处理服务器上意外的本地修改
  • --delete — webroot 严格镜像仓库，仓库里删的文件 webroot 也会删
  • script_stop: true — 任何一步失败立刻中止，不会"半部署"
  • 需要 NOPASSWD sudo — 写 /var/www 必须，CI 没法输密码

⚠️ 真实踩到的三个坑

不是我想夸张做戏 — 这套上线时第一次 CI 就 fail，后面又发现安全问题。三个都有教育价值，记一下:

坑 1 · 工具缺失

症状: 首次 CI 失败,日志: sudo: rsync: command not found

根因: Alibaba Cloud Linux 4 默认没装 rsync。一直手动 cp 用得没发现。

修复: sudo dnf install -y rsync。教训 — CI 用什么工具，先在目标机上验证。

坑 2 · rsync 把 .git 也同步了

症状: 部署完看 webroot,发现多了 .git/ .github/ nginx/ scripts/ 这些目录。

根因: 最初的 rsync 规则是 

--include='*.html'
--include='*/'      ← 这一行允许递归进入所有目录
--exclude='*'

--include='*/' 让 rsync 遍历所有目录但只复制 .html 文件 — 文件是对的，但空目录被创建出来了，包括 .git/。

修复: 加 --exclude='.*'、--prune-empty-dirs、--delete 三连。 --prune-empty-dirs 是最关键的一个 — 不会创建/保留空目录。

坑 3 · 残留 .bak 文件可公开访问

症状: curl https://blog.shiyao.pro/index.html.bak.20260604 返回 200，内容是早期占位页。

根因: 之前手动调试时为了安全留了 .bak 备份，CI 上线后忘了清。nginx 默认对 .bak 没特殊处理，所以可以直接访问。

修复: 两道防御。

  1. 立即从 webroot 删干净 + rsync 加 --exclude='*.bak*'
  2. nginx 加一条 location 屏蔽，万一 rsync 漏了也访问不到: 
    location ~* \.(bak|orig|tmp|swp|swo)(\..+)?$ {
    deny all;
    access_log off;
    log_not_found off;
}

🛡 三道防御纵深

修完上面三个坑，整套系统现在有三层独立防御应对"敏感文件意外暴露":

层内容能挡住什么
1. 仓库 .gitignore *.pem *.key .env secrets/ 本地误 git add 敏感文件
2. CI rsync 规则 --exclude='.*' --exclude='*.bak*' --prune-empty-dirs 即使仓库里有点文件，也不会同步进 webroot
3. nginx location 规则 /\. 和 \.(bak|orig|tmp|swp)$ 都 deny all 即使文件在 webroot 里,nginx 也直接返回 403

任何一层独立都能挡，但任何一层单独失效，剩下两层还在。这就是 defense in depth 的精神 — 不假设某一层 100% 可靠。

🔁 现在的工作流

写一篇新文章的全部步骤现在长这样:

# 1. 拉最新
cd ~/projects/blog-shiyao-pro && git pull

# 2. 写文章
vim new-post.html
# (改 index.html 加一条链接)

# 3. 提交推送
git add new-post.html index.html
git commit -m "post: 新文章标题"
git push

# 4. (可选) 看 CI 跑得怎样
gh run watch

就这。第 4 步还可以省 — 反正 10 秒后博客自己就更新了，相信 CI。

📝 这套方案适合谁

  • 个人博客 / 文档站 / Landing page — 任何全静态、低频更新的内容
  • 单人或两三人小团队 — 不需要复杂的 review 流程
  • 已经有云服务器的人 — 不想额外买 GitHub Pages 或 Vercel
  • 喜欢"自己掌控部署链路"的人 — 没有黑盒，每一步都看得见

不适合谁:

  • 高频更新（一天几十篇）— CI 排队和限流会变成瓶颈
  • 对部署延迟敏感（<1 秒）— rsync + ssh 链路有 ~10 秒固定成本
  • 团队 > 10 人 — 应该上正经 CDN + 静态托管
